# The app: TanStack Start on Workers

Everything that runs per request (the club's members' area and admin, sign-in, payments, Social) is one TanStack Start app in `app/`, deployed as the `better-accountant` Worker. Astro builds only the marketing pages, as static files the app serves. There are no users yet, so nothing is migrated: the Worker keeps its name and its `ClubStore`.

## Decisions

- **One Worker.** `app/cloudflare.config.ts` names `better-accountant`, exports `ClubStore`, runs the hourly job and serves the club's host, `www` and the social host. `app/src/server.ts` is the entry: CHIP and unsubscribe posts first, then the app.
- **Shared server code.** `src/server/*` (the store's modules, migrations, letters, jobs, payments) and `src/data/*` are framework-free and imported from the app by relative path. Their tests, and the app's (`app/src/**/*.test.ts`), run with `pnpm test` at the root. Rules that change data belong there, not in server functions (ADR-0001, `docs/adr/0001-domain-modules-own-data-rules.md`).
- **Sign-in is the app's own.** The `sign_ins` table keeps a hash of each session token and the member's epoch. `app/src/lib/session.server.ts` reads the `session` cookie once per request (`currentMember()`), and sets or clears it. In production the cookie is on the whole domain, so both hosts share it.
- **Hosts.** Social's routes live under `app/src/routes/social/`. The router's `rewrite` (`app/src/lib/hosts.ts`) maps the social host's `/x` to `/social/x` and back, on the server and in the browser. On a dev host the same pages are at `/social/x`, or at `social.localhost:<port>/x`.
- **Marketing.** Astro builds the marketing pages to `.site/` (`about.html`, `programmes/ai.html`), which is the app's public folder. Files are served by exact path. On the club's host the Worker maps `/about` to `/about.html` and falls through to the app when no file matches. Build Astro before the app: `pnpm --dir .. build` runs first in the app's `build` and `deploy` scripts. Pages that read the store or the member (`prerender = false` in Astro) move to the app; a members-only post body must never be in static HTML.
- **Config values.** `app/cloudflare.config.ts` must not import modules the Worker also imports: the dev server then fails to load them. It repeats the domain instead.

## Conventions for porting a page

- **Same paths.** A route keeps the Astro page's URL exactly. Links already sent in emails depend on it.
- **Same markup and classes.** Port the HTML element for element. Global classes (`btn`, `input`, `field`, `wrap`, `night`, `label`, `serif`, Social's `card`, `page`, `kicker` and the rest) stay as strings. An Astro component's scoped `<style>` becomes a co-located `X.module.css`; reach global classes inside it with `:global(.btn)`.
- **Who may do what.** `app/src/lib/access.ts` decides it, per access level: `anyone`, `member` (signed in), `paid` (paid or in grace; admins never pay), `profile` (has a Social handle) and `admin`. A loader or server route calls `admit(level, away)` from `access.server.ts` for who acts, and `away` says where everyone else goes: `toClub` (sign in and come back to the path and query, pay, or the members' area), `hidden` (a 404), or the route's own. `check(level)` answers the decision without throwing. The `/members` and `/admin` layouts ask the `gate` server function in `beforeLoad`, since they run in the browser too. Never check `role` or billing by hand.
- **Reading data.** A route's `loader` calls a `createServerFn({ method: 'GET' })` in `app/src/functions/<area>.ts`. It uses `admit` for a page that needs access, `currentMember()` for an optional viewer, and `withStore` for its reads. Missing records `throw notFound()`.
- **Store calls are RPC.** Every call into the store crosses to the Durable Object and returns a promise of the domain module's own plain data (`Store` in `src/server/instance.ts`). A server function returns it as it is; there is nothing to copy off it.
- **Changing data.** One `createServerFn({ method: 'POST' })` per form: type the input with `.validator((input: X) => input)`, then `.handler(action({ access, input: schema, limit, refusals }, async ({ actor, input, store, send }) => ...))` from `app/src/lib/action.server.ts`. The action checks access, then parses, then throttles, then runs the work, always in that order. The work calls the open `store`, queues letters with `send` (they go only if it succeeds), and answers an `Outcome` (`app/src/lib/outcome.ts`) or the domain module's failed `Result`, which `refusals` turns into its message. Refusal tables stay `Record<Reason, string>`, so every reason has a message. A form with no fields takes `input: z.undefined()`. Build emailed links with `absolute` (`mail.server.ts`).
- **Testing the app.** `action.ts` and `access.ts` are framework-free behind an `Adapter`; `action.test.ts` binds one over node:sqlite with a fixed member, a throttle that answers as told and recorded letters. Test a new pipeline rule there, and a new data rule in its domain module.
- **Forms.** A React form runs its server function through `useAction` (`app/src/components/useAction.ts`): busy while it runs, the refusal, and the page's loaders run again as its `refresh` says (`'success'`, `'always'` for admin pages, `'never'` for a form that shows its own answer or navigates). Wire each input with `action.field(name, { id, hint })` and spread `field.input` on it, so `aria-invalid` and `aria-describedby` come from one place, and show the error with `<FieldError field={field} />`. A form with no hook (a plain post answered by a loader) uses `wireField` from `app/src/lib/form.ts`. A message that names no field (`action.failure`, or `failureOf(outcome)`) shows in a `role="alert"` paragraph. Keep the copy of every message word for word.
- **Browser scripts.** An Astro `<script>` becomes React state or a `useEffect`. Reuse `src/lib/*.ts` helpers where they are framework-free.
- **Titles.** `head: () => ({ meta: [...clubTitle('Name')] })` or `socialTitle`. Add `noindex` where the Astro page had it. Social pages set `staticData: { section }` for the nav.
- **Links between hosts.** `socialHref`, `clubHref` and `socialSignInHref` from `app/src/lib/links.ts`.
- **Types.** Never `any`, `as unknown as`, `@ts-ignore` or `@ts-expect-error`. `npx tsc --noEmit` in `app/` must pass.

## Running it

- `cd app && SITE_URL=http://localhost:4178 VITE_LOCAL_SEED=on CLOUDFLARE_VITE_FORCE_BUILD_OUTPUT=true npx vite build && npx vite preview --port 4178 --host 127.0.0.1`. The dev server works too (`npx vite dev`), but browse loses its tab on it.
- `GET /dev-seed` on that build makes `team@local.test` (admin, handle `team_reviewer`) and `a@`, `b@`, `c@local.test` (Social members; a and b ticked), all with the password `local test password 1`. The route is compiled out unless `VITE_LOCAL_SEED=on`.
- `GET /dev-seed?as=a@local.test` also signs that account in and sets the cookie. Use it in browse and with `curl -c`/`-b`: Chrome drops browse's connection as soon as a password field holds a value, so never type into the sign-in form.
